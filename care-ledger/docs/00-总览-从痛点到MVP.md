## 1. 痛点（真实世界，有据可查）

照护质量是典型的信任品：家属看不见凌晨三点的护理站，监管看不见每一班的巡查——**服务过程无法被看见，只能被证明**：

- **记录义务是强标与部门规章的双保险**：[GB 38600-2019](14-调研来源.md#1-法规与标准直接依据原文已核验)（养老服务领域第一个强制性国标，2022-01-01 全面实施）把"九防"风险评估与防护变成强制底线；[《养老机构管理办法》（民政部令第 66 号）](14-调研来源.md#1-法规与标准直接依据原文已核验)要求入院评估（15 条）、24 小时值班（28 条）、应急预案与定期演练（31 条）、信息档案保存 ≥ 协议期满后五年（32 条），且民政部门**每年至少一次现场检查**（38 条）、双随机对高风险机构提高频次（39 条）——未按强标提供服务，责令改正、警告，情节严重可处 3 万元以下罚款（46 条）。
- **纠纷的举证压力全在机构一侧**：民法典第 1198 条安全保障义务下，跌倒、噎食、压疮、走失四类事故的裁判焦点是"照护是否到位、发现是否及时、是否通知了家属"（行业通识口径，见[调研来源](14-调研来源.md#3-行业与判例口径诚实标注)）——而这三问的答案全部落在记录上，拿不出记录就要吃下更大的责任比例。
- **周期义务靠记性**：评估复评、应急演练、员工健康体检，"定期"两个字在纸本时代全靠老板娘的脑子。
- **现状解法 = 挂墙的纸本交接本 + 记忆 + 微信语音**：巡查做了、字也签了，但纸本经不起"连续 90 天逐日核对"；出了事连夜补记录，字迹时间全是破绽。
- 第一性差距：**"照护持续在发生"与"能证明照护持续在发生"之间，没有任何小微级工具把它变成一本连得起、拿得出的账**——智慧养老平台服务大型机构（数万元全家桶），政府平台只管报送，10~100 床的民办院被整个市场排除在外。

## 2. 方案（机会 → 产品）

**护安单**：零依赖、本地优先的 PWA。

1. **老人建档 + 九防评估**：档案即体检表——防噎食/防误食/防压疮/防烫伤/防坠床/防跌倒/防走失/防他伤自伤/防活动意外，四级登记（❓ 未评估 / ✅ 无此风险 / 🛡️ 需防护 / 🔴 高风险），建档即全「未评估」：把"没评过"从默认状态变成必须消灭的待办；watch/high 强制写防护措施。
2. **每班 30 秒打卡**：署名 + 交接要点 + 一键平安；同班次唯一、异常强制写处置、夜巡次数不足自动亮灯（short 点名不阻止）；缺班自动点名——记录连续性第一次有人盯。
3. **事件闭环门禁**：跌倒/噎食/走失等事件登记后，**家属告知（时间+方式+通知人）与复盘整改填不齐，工具拒绝结案**——66 号令第十九条"转送救治并通知紧急联系人"被做成了硬约束，未闭环一直亮灯。
4. **周期义务账**：评估复评/应急演练/员工体检到期、临期点名，完成打勾自动滚动下一轮——"定期"从口号变成日历。
5. **照护安全自证包三通道**（核心"信任交付"动作）：按老人 × 时段一键生成——微信文本（主通道）、打印版单文件 HTML（含查阅签字栏）、直接打印；**记录缺口如实列出，不掩饰**：检查现场"连不上"比"有缺口但补得诚实"更致命。
6. **数据自持**：100% 本地存储（本地优先本身就是 66 号令第 32 条个人信息保护义务的实现方式），JSON 导出/导入，本地埋点支持验证闭环。

## 3. 诚实的现状声明（真实可落地，不空中楼阁）

- **已验证**（本仓库内可复现）：核心逻辑 21/21 单元测试通过（含打卡唯一性、异常强制留痕、夜巡 short 点名、事件闭环门禁与撤销回滚、周期滚动边界、自证包缺口诚实列出、XSS 转义、导入导出往返）；浏览器端到端全流程（示例数据 → 看板六类预警 → 夜班打卡 → 事件空字段拒绝结案 → 补全告知复盘后闭环 → 自证包生成）真实运行通过；打印版 HTML 为单文件、离线可用；零 npm/CDN/API 依赖；SW 缓存版本化。
- **未验证**（需真实用户，见 docs/13 假设登记册）：评估建档留存（H1）、打卡留存（H2）、事件闭环使用（H3）、出证真实使用（H4）、付费意愿（H5）、供应商渠道（H6）——全部标注"待验证"并配有可证伪判据。
- **边界与免责**：不做呼叫/IoT 硬件、不做民政报送、不做医疗膳食档案、不碰收付费与招生；自证包是机构自查与沟通记录，不宣称司法级存证，不替代法定档案、视频监控与报送；属地口径（夜巡次数、复评与演练周期）全部参数化——**属地要求永远赢**；不提供"补记洗白"，补记必须注明。

## 5. 与既有项目的领域隔离（用户约束）

本方向为**养老机构服务安全台账（民政监管线 · B2B · 10~100 床民办机构 · 机构侧照护证明基建）**，已对照仓库根 README 领域登记表（第 1~10 号）做领域排除：不与宠托付（C 端宠物照护）、食安哨（餐饮食安）、翻房单（民宿周转与布草）、工据（人社用工合规）、消课单（教培预收费）、购销单（农药购销）、车况单（二手车披露）、瓶安单（燃气配送与入户安检）、灭菌单（口腔诊所器械灭菌追溯）、安巡单（工贸安全生产与动火作业）重叠——上述方向的义务来源、行业语境与付费主体均与养老服务无关。本方向属**民政线的养老服务监管语境**（服务过程证明基建：强标九防 + 部门规章值班档案义务 + 安全保障义务举证），与卫健公共场所卫生线、医疗器械院感线、应急安全生产线分属不同监管条线。与 `newidea` 仓库亦无重叠：`shadow-base` 是 C 端在职者的社保缴费基数对账（个人视角），本方向是 B 端养老机构的服务安全台账（机构视角），主体、行业、义务来源均不同。付费主体（机构与照护供应链上游供应商/保险经纪）、使用场景（收住评估/值班交接/事件闭环/迎检出证）、行业语境（强制性国标 + 部门规章 + 安全保障义务）均独立成域。
