> 项目：**翻房单 TurnSheet** —— 小微民宿退房周转执行台 + 布草供应链台账
> 仓库：`newchance` · 状态：MVP 已开发并通过端到端验证（`app/` 目录，34/34 单元测试 + 浏览器全流程）

## 1. 痛点（真实世界，有据可查）

供给过剩是民宿小微房东的世界级处境：中国民宿相关企业十年增长超 20 倍，现存约 38 万~40 万家（企查查口径；2024 底 32.3 万、2025 底 38.3 万、2026-05 约 40.3 万，[来源](14-调研来源.md#市场与行业数据)）。38 万商家抢流量，好评 = 流量 = 生存。落到一个管着 1~10 间房的房东身上，它具体成了一段每天发生两次的黑箱：

- **退房 → 入住的窗口是刚性的**：退房多在 12:00、入住多在 14:00~15:00，保洁能否在这两三个小时内完成翻房，直接决定当天间夜是否兑现、客人第一眼看到什么。
- **卫生是底线**：「一客一换」是住宿业公用品的硬性卫生要求（GB 9663-1996）；GB/T 41648-2022 把卫生与服务写入民宿国标；违反卫生义务有明确罚则（警告/罚款乃至停业整顿，[法规来源](14-调研来源.md#法规与标准)）。
- **现状解法 = 微信喊保洁 + 口头交代 + 无台账**：接重叠订单、保洁不知道截止时间、遗留物品没人记录、出了差评拿不出任何执行留档。
- **布草供应链无人记账**：几套在房、几套脏、几套在洗涤厂、几套净——全凭记忆；在途超期没人催、丢货扯皮没凭据、发灰了才想起重购。海外已有 Turno 等翻房调度公司验证这是独立痛点，但中国房东与保洁不可用；国内 PMS 只画房态色块，不管执行。
- 第一性差距：**"两次入住之间的执行确定性"没有任何工具承接**——翻房单把窗口变清单、把清单变微信消息、把布草变账本。

## 2. 方案（机会 → 产品）

**翻房单**：零依赖、本地优先的 PWA。

1. **房源/房期建档**：房源 4 项、房期 4 项，20 秒录一单；不做 OTA 直连（无授权依赖、无封禁风险、离线可用）。
2. **翻房窗口自动派生**（核心计算）：每单退房自动衔接下一单入住——窗口 < 标准保洁时间红灯、贴 1.5 倍线黄灯、订单重叠直接点名。
3. **翻房打卡留档**：查遗留 → 撤脏布 → 清洁 → 铺新布 → 补耗品 → 拍照回传六步；遗留物品单独记录。
4. **翻房任务单三通道**（核心"派工"动作）：纯文本复制微信发给保洁（主通道）、打印版单文件 HTML（含签字栏与查遗留填写行）、直接打印。
5. **布草周转账**（供应链账本）：每套「在房 → 脏 → 在途 → 净」过账，总量守恒；洗涤厂 SLA 超时点名催厂；未来 3 天到客缺口预警；按真实洗涤节奏推 90 天报废重购预算（样本不足诚实拒判）。
6. **耗品低库存 + 数据自持**：安全线管理；100% 本地存储，JSON 导出/导入。

## 3. 诚实的现状声明（真实可落地，不空中楼阁）

- **已验证**（本仓库内可复现）：核心逻辑 34/34 单元测试通过；浏览器端到端全流程（示例数据 → 看板五类预警 → 翻房打卡落库 → 布草送洗过账 → 任务单生成导出）真实运行通过；打印版 HTML 为单文件、离线可用；零 npm/CDN/API 依赖；SW 缓存版本化且更新可靠（`cache:'reload'`）。
- **未验证**（需真实用户，见 docs/13 假设登记册）：房期录入留存（H1）、派单真实使用（H2）、布草记账坚持（H3）、付费意愿（H4）、洗涤厂渠道（H5）——全部标注"待验证"并配有可证伪判据。
- **边界与免责**：不做 OTA 直连与 PMS 功能；本地记录不宣称司法级存证；额定洗涤次数与 SLA 是可覆盖的行业先验参数；工具不替代卫生许可与法定检查。

## 5. 与既有项目的领域隔离（用户约束）

本方向为**民宿短租 · 退房周转执行与布草供应链台账（B2B prosumer · 小微房东 · 住宿业运营）**，已对照仓库根 README 领域登记表与 `newidea` 仓库 62 个点子做领域排除：不与 `pet-handoff`（C 端宠物照护）、`food-sentry`（B2B 餐饮合规/监管科技）、`newidea`（个人/家庭账本经济学 + 开发者工具，无任何住宿业/短租运营方向）重叠。付费主体（民宿房东与洗涤厂）、使用场景（两次入住之间的运营执行）、行业语境（住宿业卫生与服务标准）均不同域。
