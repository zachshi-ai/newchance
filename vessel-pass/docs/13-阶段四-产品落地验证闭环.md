# 13 · 阶段四：产品落地验证闭环

## 1. DSTE 主线（从战略到执行）

市场洞察（运力出清+船员老龄化+扣船级罚则，docs/10）→ 战略意图（内河个体船东合规台账的事实标准）→ 创新焦点（开航五道闸+当次开航单）→ 业务设计（燃油供应点/船舶经纪白标为主、船东订阅为辅）→ 关键任务（本 MVP：引擎与出证闭环；下一程：单水系渠道试点）→ **已执行到「关键任务」的 MVP 交付**：23/23 单测+27/27 E2E 落地。

## 2. MVP 定义与已验证部分

- **已验证（技术可行性）**：23/23 单元测试 + 27/27 浏览器端到端（冷启动→示例→看板红灯→三连拦截→整改销案→过闸开航→月报→出证→持久化→备份），全程零页面错误；本地优先离线可用落地。
- **待验证（商业假设）**：全部标注如下，不把未验证的信念当成果。

## 4. OHELM 循环（假设→风险→出证→学习→测量）

以 H2/H3 为例跑通闭环：**假设**「每日自查+五道闸形成依赖」→ **风险**「被当作检查前突击工具」→ **出证物**：traces 使用记录（含 voyage-blocked 埋点，本机导出）→ **学习**：若拦截次数高且留存高=依赖成立；若留存低=被当突击品，需把闸机前移到自查提醒 → **测量**：周留存、拦截/船/周、出证次数。每 30 天一次 OHELM 复盘，砍掉最弱功能。

## 5. 北极星指标与护栏

- **北极星**：周活跃开航船数（一周内开出 ≥3 张开航单的船）——同时代表真实营运与合规执行。
- **护栏**：数据导出率（防锁定感知）、拦截理由阅读完成率（法条解释被读=信任建立）、证书与人员信息出本机次数（恒为 0）。

## 7. 诚实条款

以上商业假设全部未验证；仓库内验证的只有技术可行性与法条口径的准确性（docs/14 全部一手来源）。我们不把「做了 MVP」当「验证了需求」。
